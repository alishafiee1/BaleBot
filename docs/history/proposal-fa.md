# پروپوزال: بازطراحی ربات بله (BaleBot) روی هرمس

نسخه‌ی پیشنهادی ۱ — بر پایه‌ی بررسی `bale_bridge.py` فعلی (۴۲۸ خط، تک‌فایل، تک‌کاربره)

## ۱. هدف
تبدیل پل تک‌کاربره‌ی فعلی به یک **سرویس چندکاربره** با:
- اتصال خودکار هر کاربر پس از `/start` به «مدل پایه» (تعیین‌شده در پنل وب ادمین)
- ۱۰۰ درخواست رایگان روزانه برای هر کاربر روی مدل پایه
- ثبت کلید API شخصی کاربر از هر سایت، با ساخت خودکار مسیر اتصال توسط هوش مصنوعی
- انتخاب مدل از منو (مدل‌های پایه + مدل‌های کاربر)
- اجرای ابزارهای هرمس برای کاربران، **در سندباکس**، بدون امکان آسیب به سرور یا تغییر کد
- پنل وب مدیریت

## ۲. وضع فعلی و ضعف‌ها
| مورد | وضع فعلی |
|---|---|
| کاربر | فقط یک مالک (`BALE_ALLOWED_USERS`) |
| ساختار | تک‌فایل، متغیر سراسری، بدون تست |
| اجرا | root، بدون محدودیت systemd |
| کلیدها | همه در یک `.env` |
| وضعیت | فایل JSON تکی، بدون پایگاه داده |
| مدل | ثابت در کد/کانفیگ |

## ۳. معماری پیشنهادی

```
 Bale  <──>  Bot Gateway ──> Core API ──> Model Router ──> مدل پایه / مدل‌های کاربر
                                  │             │
                                  │             └─> Key Vault (رمزنگاری‌شده)
                                  ├─> Quota Service (Redis)
                                  ├─> PostgreSQL
                                  └─> Agent Runner ──> سندباکس Incus به‌ازای کاربر ──> ابزارهای هرمس
 Admin Panel (وب) ──> Core API
```

**مؤلفه‌ها**
1. **Bot Gateway** — دریافت پیام از بله (webhook یا long-polling)، حذف منطق از لایه‌ی شبکه، فقط ترجمه‌ی پیام به رویداد داخلی.
2. **Core API** — منطق اصلی: کاربران، گفتگوها، سهمیه، مدل‌ها، کلیدها. REST داخلی + همین API برای پنل وب.
3. **Model Router** — لایه‌ی واحد فراخوانی مدل با رابط سازگار با OpenAI. انتخاب مدل بر اساس تنظیم کاربر، کسر سهمیه، fallback.
4. **Key Vault** — ذخیره‌ی رمزنگاری‌شده‌ی کلیدهای کاربران.
5. **Quota Service** — شمارنده‌ی روزانه در Redis، ریست ساعت ۰۰:۰۰ به وقت تهران.
6. **Agent Runner** — اجرای هرمس برای هر کاربر در سندباکس.
7. **Admin Panel** — پنل وب مدیریت.

**پشته‌ی پیشنهادی:** Python 3.13 + FastAPI (ادامه‌ی کد فعلی)، PostgreSQL، Redis، Docker/Incus، پنل با Next.js یا HTMX. (اگر ترجیح می‌دهید هم‌پشته با RODO باشد: NestJS + Prisma.)

ساختار پوشه‌ها:
```
balebot/
  gateway/   core/   router/   vault/   quota/   runner/   admin/
  tests/     migrations/   deploy/ (systemd, incus profiles)
```
استانداردها: `ruff` + `mypy` + `pytest`، پیکربندی با env، لاگ ساخت‌یافته با شناسه‌ی همبستگی، CI.

## ۴. جریان کاربر
1. `/start` ← ساخت کاربر، اتصال به مدل پایه‌ی فعلی، پیام خوش‌آمد و نمایش سهمیه‌ی باقی‌مانده.
2. پیام عادی ← کسر یک واحد از ۱۰۰ درخواست روزانه ← پاسخ مدل پایه.
3. سهمیه تمام شد ← پیام راهنما: «فردا ریست می‌شود یا کلید خودت را اضافه کن». درخواست‌های روی **کلید شخصی** از سهمیه کم نمی‌شوند.
4. `/menu` ← انتخاب مدل، حالت فکر کردن، گفتگوی تازه، مصرف، کلیدهای من.

قوانین سهمیه: فقط پاسخ موفق شمرده می‌شود؛ سقف طول ورودی/خروجی؛ محدودیت نرخ (مثلاً ۱۰ پیام/دقیقه)؛ فایل و ویس هزینه‌ی بیشتر (قابل تنظیم در پنل).

## ۵. افزودن کلید API توسط کاربر
مثال: «می‌خواهم از سایت فلان کلید بدهم».

1. ربات نام سایت را می‌پرسد و کلید را می‌گیرد.
2. **بلافاصله پیام حاوی کلید را از چت حذف می‌کند** (`deleteMessage`) و هشدار می‌دهد که کلید را در پیام عادی نفرستد.
3. **ساخت مسیر ارتباط توسط هوش مصنوعی پیش‌فرض:**
   - مدل مستندات سایت را از طریق ابزار دریافت وب با allowlist می‌خواند.
   - خروجی او یک **پیکربندی اعلانی (JSON)** است، نه کد: `base_url`، نوع احراز هویت، مسیر chat، مسیر فهرست مدل‌ها، قالب درخواست/پاسخ.
   - بیشتر سرویس‌ها سازگار با OpenAI هستند؛ ابتدا همین حالت امتحان می‌شود.
4. اعتبارسنجی خودکار: یک درخواست آزمایشی کوچک + دریافت فهرست مدل‌ها.
5. کاربر مدل‌های کشف‌شده را در منو می‌بیند.

**اصول امنیتی این بخش (مهم):**
- **مدل هرگز کلید را نمی‌بیند.** در پرامپت AI فقط نام ارائه‌دهنده و مستندات می‌رود؛ کلید را فقط Model Router هنگام ارسال درخواست جایگزین می‌کند.
- جلوگیری از نشت کلید به دامنه‌ی مهاجم: دامنه‌ی `base_url` به کاربر نشان داده و تأیید گرفته می‌شود؛ فقط `https`؛ آدرس‌های خصوصی/محلی/metadata (SSRF) مسدود؛ قالب‌های ارائه‌دهنده‌ی پرکاربرد را ادمین می‌تواند از پیش تأیید کند.
- ذخیره: رمزنگاری AES-256-GCM (envelope encryption)؛ کلید اصلی خارج از پایگاه داده (فایل با مجوز 600 یا KMS)؛ هر کلید فقط با `user_id` صاحبش قابل رمزگشایی.
- کلید در لاگ، خطا و پنل ادمین **ماسک** می‌شود (فقط ۴ کاراکتر آخر). ادمین هم نمی‌تواند کلید کاربر را ببیند.
- دستور `/keys` برای فهرست، آزمون و حذف کلید.

## ۶. مدل‌ها و منو
- جدول `models`: مدل‌های پایه (مدیریت ادمین) + مدل‌های کلید کاربر (خصوصی).
- منوی هر کاربر فقط مدل‌های پایه‌ی فعال + مدل‌های **کلیدهای خودش** را نشان می‌دهد.
- ادمین می‌تواند مدل را فعال/غیرفعال، قابلیت‌ها (متن، تصویر، ویس) و هزینه‌ی سهمیه را تعیین کند. تغییر مدل پایه در پنل بلافاصله اعمال می‌شود.

## ۷. اجرای ابزارهای هرمس با امنیت
هدف: کاربران از ابزارها استفاده کنند، ولی نتوانند به سرور آسیب بزنند یا کد را عوض کنند.

لایه‌های دفاعی:
1. **جداسازی:** هر کاربر یک کانتینر Incus غیرممتاز با پروفایل محدود (یا یک پول کانتینر با workspace جدا). کاربر `root` میزبان هرگز وارد نمی‌شود.
2. **فایل‌سیستم:** کد برنامه، کانفیگ و `.env` در سندباکس **mount نمی‌شوند**؛ فقط `/workspace` کاربر قابل نوشتن است (سهمیه‌ی دیسک). بقیه فقط‌خواندنی.
3. **منابع:** محدودیت CPU، رم، تعداد پروسه، دیسک و زمان اجرا برای هر درخواست.
4. **شبکه:** خروج فقط به اینترنت عمومی؛ **مسدودسازی** LAN، Incus bridge، `127.0.0.1` میزبان و metadata. فقط پورت‌های مجاز.
5. **ابزارها:** allowlist ابزار برای هر سطح کاربر (مثلاً: جستجوی وب، تحلیل تصویر، اجرای کد در سندباکس: بله؛ shell روی میزبان، تغییر کانفیگ هرمس، cron سراسری: خیر). ادمین از پنل مدیریت می‌کند.
6. **اعتبارنامه:** هیچ کلید سرور در سندباکس نیست. دسترسی به مدل از طریق Model Router با توکن کوتاه‌عمر.
7. **کد غیرقابل تغییر:** مالک فایل‌های برنامه root، مجوز فقط‌خواندنی؛ سرویس با کاربر غیر root و `NoNewPrivileges`، `ProtectSystem=strict`، `ReadWritePaths` محدود.
8. **ممیزی:** ثبت هر اجرای ابزار (کاربر، ابزار، زمان، نتیجه) و هشدار به ادمین برای الگوهای مشکوک.

## ۸. پنل وب مدیریت
بخش‌ها:
- **داشبورد:** کاربران فعال، درخواست‌ها، خطاها، مصرف، سلامت سرویس‌ها
- **مدل پایه:** انتخاب مدل پایه و fallback، پرامپت سیستم، پارامترها
- **ارائه‌دهندگان و مدل‌ها:** مدیریت قالب‌ها، تأیید قالب‌های ساخته‌شده توسط AI
- **کاربران:** جستجو، مسدودسازی، تغییر سهمیه‌ی هر کاربر، سطح ابزار
- **سهمیه:** سقف روزانه‌ی پیش‌فرض (۱۰۰)، ساعت ریست
- **ابزارها و سندباکس:** allowlist، محدودیت منابع، وضعیت کانتینرها
- **گزارش‌ها:** ممیزی، لاگ خطا
- **اعلان همگانی** به کاربران

امنیت پنل: فقط روی شبکه‌ی خصوصی/پشت reverse proxy با HTTPS؛ نرخ‌گیری تلاش ورود؛ نشست امن و CSRF؛ احراز هویت دومرحله‌ای اختیاری.

**دسترسی اولیه به پنل:** نام کاربری و رمز اولیه‌ی ادمین هنگام نصب **تصادفی ساخته می‌شود** و یک‌بار در ترمینال شما نمایش داده می‌شود (نه در این سند و نه در گیت). در اولین ورود تغییر رمز اجباری است. رمز در پایگاه داده فقط به‌صورت هش (argon2) ذخیره می‌شود.

## ۹. الهام از Grok (قابلیت‌های پیشنهادی)
- **جستجوی زنده‌ی وب با ارجاع به منبع** و حالت «تحقیق عمیق» (DeepSearch)
- **حالت فکر کردن** (Think) — در ربات فعلی هست؛ نگه داشته شود
- **درک تصویر** و تولید تصویر
- **ویس به متن** و پاسخ صوتی
- **حالت‌های شخصیتی** (رسمی، دوستانه، طنز، معلم، برنامه‌نویس)
- **حافظه‌ی بلندمدت** اختیاری با دستور «فراموش کن»
- **کار زمان‌بندی‌شده** (یادآوری، گزارش روزانه، پایش خبر) — مشابه Tasks
- **گروه‌ها و کانال‌ها:** پاسخ با منشن، خلاصه‌سازی گفتگوی گروه
- **تحلیل اسناد** (PDF، فایل، جدول) و اجرای کد برای محاسبه/نمودار
- **اشتراک‌گذاری گفتگو**، برگه‌ی مصرف و دکمه‌های بازخورد 👍/👎

پیشنهاد اولویت: وب‌جستجو، درک تصویر/اسناد، حالت‌های شخصیتی، وظایف زمان‌بندی‌شده؛ سپس حافظه و گروه.

## ۱۲. ریسک‌ها
- نشت کلید یا ارسال به دامنه‌ی مخرب ← بخش ۵ (تأیید دامنه، SSRF، رمزنگاری)
- سوءاستفاده از ابزارها و فرار از سندباکس ← بخش ۷ + بروزرسانی منظم Incus
- هزینه‌ی مدل پایه با رشد کاربران ← سقف سراسری روزانه و هشدار هزینه در پنل
- محدودیت‌های API بله (دکمه‌ها، اندازه‌ی فایل، نرخ پیام) ← صف و تلاش دوباره
- ریسک حقوقی/حریم خصوصی ذخیره‌ی گفتگوها ← مدت نگهداری قابل تنظیم و حذف توسط کاربر

## ۱۳. پرسش‌های باز
1. وب‌هوک یا long-polling؟ (دامنه‌ی عمومی با HTTPS دارید؟)
2. مدل پایه‌ی اولیه همان `glm-4.7-flash` باشد؟
3. پشته: Python/FastAPI یا NestJS؟
4. سندباکس: یک کانتینر به‌ازای هر کاربر یا پول مشترک با workspace جدا؟
5. آیا گفتگوهای کاربران ذخیره شود؟ تا چه مدت؟
6. ربات در گروه‌ها هم کار کند؟
